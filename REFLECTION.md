## 1. The hardest bug you hit this week, and how you debugged it

The hardest bug was a silent data consistency issue that appeared after I refactored the audit engine from "first-match wins" to exhaustive multi-finding evaluation.

The original engine had a `break` statement — it would find the first matching rule for a tool, generate one recommendation, and stop. This meant if a company had both an enterprise overkill problem and overlapping chat assistants, only one issue appeared in the report. I wanted the engine to surface all relevant findings together because that is how a real audit works.

After removing the `break` and accumulating all matching findings, the financial totals started breaking. The optimized spend values were wrong, grouped recommendation cards showed inflated savings, and stacks that should have scored 85+ were landing around 60. The UI looked fine visually — the numbers just did not add up.

I initially assumed it was a rendering issue because recommendation cards were duplicating. Then I suspected Zustand hydration was corrupting the state between page navigations. Both were wrong.

After several failed attempts, I started debugging each layer independently:
- logged raw recommendation arrays directly from the engine output
- compared expected vs actual spend calculations by hand
- simulated specific tool stacks and manually predicted what the output should be
- isolated the score calculator and fed it known inputs

The actual root cause turned out to be in the score calculator. KEEP verdicts — findings that say "this tool is fine, no changes needed" — were being treated as penalty-generating recommendations because they inherited the same high confidence values as actionable findings. The scoring loop was penalizing tools that were already well-optimized, which dragged down the entire stack score.

The fix was adding an explicit `optimizationCategory: 'keep'` type and skipping those entries during penalty calculation in `scoreCalculator.ts`. I also had to update `spendCalculator.ts` to prevent grouped recommendations from being double-counted when summing optimized costs.

That bug taught me that the hardest issues are usually not where you first look. It was not a UI bug or a state bug — it was a type classification problem buried two layers deep in the calculation pipeline.

## 2. A decision you reversed mid-week, and what made you reverse it

Early in the project I planned to use AI-generated recommendations as the primary intelligence layer. I wanted the audit engine to feel genuinely smart, so my first approach was to pass tool configuration data directly to Gemini and have it generate optimization recommendations and savings estimates in natural language.

After building the first version, I realized the outputs were unreliable. The same tool stack would produce noticeably different recommendations depending on minor prompt variations. Savings estimates were sometimes exaggerated — a solo developer using two subscriptions would get a recommendation claiming $500/month in potential savings, which is clearly wrong. Debugging was also painful because the reasoning was hidden behind opaque API responses instead of traceable logic.

Mid-week I reversed the decision completely. I moved all financial logic and recommendation generation into a deterministic rule engine:
- a centralized pricing catalog with real 2026 per-seat costs
- capability overlap rules based on simple category groupings
- seat inefficiency and enterprise rightsizing checks
- weighted optimization scoring with explicit penalty factors

AI was kept in the project, but only for generating the narrative summary paragraph at the end of the report — presentation, not decision-making. The summary is generated by Gemini 2.5 Flash through a server-side API route, and if the API fails for any reason, a deterministic local fallback renders instead. The product never appears broken regardless of API state.

This reversal improved the product significantly. The engine became explainable, testable, and predictable. I could manually simulate a tool stack, predict what the output should be, run the engine, and verify the result matched. That was impossible with the AI-first approach.

In hindsight, using AI for presentation and deterministic logic for decisions was the right trade-off for an MVP with limited development time. If I had more time, I might explore a hybrid approach — but the core financial calculations should always be deterministic.

## 3. What you would build in week 2 if you had it

If I had another week, I would focus on making the audit inputs smarter rather than adding more UI features.

The biggest limitation right now is that the engine relies entirely on self-reported data. Users manually select their tools, plans, and seat counts. In a real product, this information should come from actual workspace integrations. I would prioritize building connectors for:
- billing APIs from OpenAI, Anthropic, and Cursor to pull real spend data
- SSO or SCIM integrations to detect actual active seat counts vs provisioned seats
- basic login frequency tracking to identify zombie licenses

This would eliminate the manual entry friction and make recommendations significantly more accurate. Right now the engine cannot detect that someone is paying for 10 Cursor seats but only 4 people logged in last month. With real telemetry, it could.

The second major addition would be persistent organization workspaces with authentication. Currently every audit is a one-shot snapshot. Users get a shareable report URL but there is no way to save multiple audits, track spend changes over time, or revisit previous optimization recommendations. Adding Supabase Auth, saved audit history, and a lightweight dashboard showing spend trends would make the product feel like a real SaaS tool instead of a calculator.

I would also improve recommendation prioritization. The current system is manually weighted — each scoring factor has a hardcoded penalty value. In week 2 I would experiment with data-driven weighting: tracking which recommendations users actually act on and adjusting confidence scores based on acceptance rates across similar team profiles.

Finally, I would improve the consultation workflow with basic CRM integration — automated lead scoring, follow-up email sequences, and conversion tracking. The current lead capture form works, but there is no pipeline visibility after submission.

## 4. How you used AI tools

AI tools were heavily involved throughout the project, but I used them as engineering accelerators rather than autonomous builders.

**Antigravity** was my primary development environment. I used it for the majority of the work — building components, debugging engine logic, iterating on the audit flow, and handling deployment issues. It was especially useful for rapid iteration cycles where I needed to make a change, test it, and adjust quickly. The engine refactoring from first-match to exhaustive evaluation was done almost entirely through Antigravity.

**GitHub Copilot** handled most of the repetitive TypeScript scaffolding — interface definitions, import statements, boilerplate component structure. It saved time on mechanical code but I never relied on it for logic decisions.

**Gemini 2.5 Flash** is integrated into the product itself as the AI summary provider. It generates the narrative paragraph at the end of audit reports through a server-side API route. I spent some time prompt-engineering the system message to produce calm, advisor-like summaries instead of generic marketing language.

Where AI tools failed me:
- The KEEP verdict scoring bug was introduced during an AI-assisted refactor. The generated code looked correct — the recommendations rendered properly in the UI — but the scoring engine was silently penalizing healthy stacks because KEEP findings inherited penalty weights. I only caught it by manually testing edge cases and comparing expected vs actual scores.
- AI-generated enterprise downgrade recommendations were too aggressive. The engine would recommend dropping Enterprise plans even for teams that might genuinely need compliance or admin features at that tier. I had to manually calibrate confidence thresholds and add team-size-aware gating.
- The `enterpriseOverkill` rule was initially using a `0.35x` price estimate for downgrade costs instead of looking up the actual catalog price. This produced wrong savings numbers that looked plausible but were inaccurate. I found this by hand-calculating expected savings for a known tool configuration and comparing it to the engine output.

Overall, AI tools probably cut development time by 40–50% compared to working without them. But every meaningful decision — pricing accuracy, scoring calibration, recommendation realism, architecture trade-offs — required manual verification. The tools were fast but not trustworthy for correctness-critical logic.

## 5. Self-rating on a 1–10 scale

### Discipline — 7/10

I shipped meaningful progress across five active development days out of seven. Two days had zero output — one was a family day after coming home from college, and one was lost to competing priorities. I could have been more disciplined about time allocation, but when I was working, the sessions were focused and productive.

### Code Quality — 7/10

The codebase is reasonably clean for an MVP built in under a week. The engine architecture separates concerns well — rules, calculators, and orchestrator are independent modules. Type safety is consistent across the audit pipeline. However, some components (especially the demo results page) accumulated tech debt from rapid iteration. I cleaned up the worst of it in the final polish pass but there are areas that would benefit from further refactoring.

### Design Sense — 7.5/10

The product looks polished for an assignment project. The audit flow feels smooth, the results dashboard is visually clean, and the recommendation cards communicate information clearly. I paid attention to details like animated score rings, staggered card entrances, and consistent spacing. The weakest area is probably the landing page, which works but does not feel as refined as the results dashboard.

### Problem Solving — 8/10

The most difficult progress came from debugging layered engine issues rather than building new features. Finding the KEEP verdict scoring bug, fixing the financial double-counting in grouped recommendations, and resolving the float precision problem all required systematic debugging instead of just writing more code. I spent significant time validating outputs by hand rather than trusting generated results, which caught several issues that would have shipped otherwise.

### Entrepreneurial Thinking — 8/10

I tried to think beyond completing screens. Features like the consultation CTA (gated behind a savings threshold), shareable reports with OG previews, lead capture forms, transactional emails, and honeypot spam protection were added to make the product feel commercially real rather than just technically functional. The audit engine produces "KEEP" verdicts specifically because real procurement tools explain what is working, not just what is broken. These decisions were driven by thinking about what would make someone actually trust the product, not just what would satisfy a feature checklist.
